> 深度研究（Deep Research）类 Agent 的后训练，难点不在算法，而在数据。这篇笔记整理一条 RL 数据从设计、质检、清洗到自动回流的完整链路。

做过 RLVR 的人都熟悉这套流程：出题、给标准答案、训练时用脚本判对错。但深度研究任务没有标准答案——同一个研究问题，好报告可以有很多种写法，没法做字符串比对。于是奖励信号只能来自一份**评分清单**。

一条数据 = 一道研究任务（`instruction`）+ 一份评分清单（`rubric`）。模型作答，judge 按 rubric 打分，分数作为 RL 的 reward：

```
① 写 instruction：一个需要多步检索的研究问题
② 写 rubric：逐条评分标准 + 权重
③ Agent 多步搜索，产出带引用的报告
④ LLM-as-judge 按 rubric 逐条打分，加权求和 = reward
⑤ GRPO / PPO 用 reward 更新模型
```

所有的数据工程工作，都发生在 ② 和 ③ 之间：确认这道题值得训练、这份评分标准可靠。

## 一、基本概念

**Deep Research Agent**：自主执行研究任务的 Agent——拆解问题 → 多轮搜索浏览 → 阅读大量来源 → 交叉验证 → 输出带引用的长报告。组成部分：规划器、搜索/浏览工具、多跳检索循环（ReAct）、报告写作。代表系统：OpenAI Deep Research、Gemini Deep Research、Anthropic Research、Perplexity、Kimi-Researcher、Tongyi DeepResearch。

**reward 的四种来源**

| RL 范式 | 奖励来源 |
|---|---|
| RLHF | 人工排序偏好，训练奖励模型 |
| RLAIF | AI 按既定原则评判 |
| RLVR | 可验证奖励：答案是否正确、代码是否通过测试 |
| RaR（Rubric-as-Reward） | 用 rubric 给开放式长文打分 |

**为什么深度研究需要 rubric**

1. 任务长程，几十步工具调用只给一个最终分过于稀疏，无法定位哪步出错；
2. 没有唯一答案，无法像数学题那样字符串比对，RLVR 失效；
3. 要奖励"有据"而非"流畅"，即声明必须被所引来源支撑。

**几个术语**

- **rubric / 条目 / 权重**：评分清单。条目要原子（只判一件事）、自包含（judge 不依赖外部知识即可判定）。
- **可验证 vs 主观**：可验证指客观能查（数字、日期、是否标注来源）；主观需要判断（如"写得好"）。设计时尽量把条目推向可验证。
- **引用忠实度（grounding）**：报告中的声明是否真被所引来源支撑，最关键也最难核验。
- **Reward Hacking**：模型钻 rubric 漏洞拿分，如凑字数、堆引用、伪造引用、语气笃定。
- **Outcome vs Process**：只评最终报告，还是也评中间研究步骤。
- **IAA（标注者间一致性）**：两人用同一 rubric 判同一报告结论是否一致；不一致说明 rubric 过于主观。

## 二、数据结构

一条数据是一个 JSON 记录，schema 参照 RaR / HealthBench。

| 字段 | 说明 |
|---|---|
| `instruction` | 给 Agent 的研究任务（题干） |
| `context` | 可选，补充背景/给定材料 |
| `rubric[]` | 评分清单：`text` 描述 · `category` 类别 · `weight` 权重 · `type` 可验证/半主观/主观 |
| `reference_answer` | 可选，参考答案 |
| `reference_sources[]` | 金标来源 URL（gold） |
| `metadata` | domain / difficulty / language 等标签 |

RaR 的几个经验值：

- 每条 rubric 含 7–20 个自包含条目；
- 条目分类加权：Essential（≈1.0，缺失即不合格）、Important（≈0.7）、Optional（≈0.3）、Pitfall（≈0.9，常见错误，通常给负分）；
- 聚合方式两种：显式 = 逐条打分加权求和；隐式 = 整份 rubric 交给 judge 出一个总分；
- rubric 通常由强模型对照参考答案生成，再由人工校验。

## 三、instruction 与 rubric 设计

instruction 决定题目是否值得训练，rubric 决定优化方向。设计目标是让 reward 的高低对应研究质量的高低。

### 3.1 instruction：5 条准则

| 准则 | 设计要求 | 自测 |
|---|---|---|
| 规格明确 | 任务、约束（时间/地域/语言/口径）、交付物（格式/篇幅/必覆盖点）都写清 | 我能复述出它要什么、交付什么吗？ |
| 可验证 | 答案存在且能被事实锚定，不基于不实前提 | 存在可核验的正确答案吗？ |
| 需要研究 | 必须多源多跳 + 交叉验证才能答 | 去掉检索还能答对吗？ |
| 中立 | 不预设结论，题干不含答案 | 题干暗示了它想要的结论吗？ |
| 自然 | 像真实研究需求，非模板拼接 | 真人会这么问吗？ |

### 3.2 rubric：5 条准则

| 准则 | 设计要求 | 自测 |
|---|---|---|
| 覆盖 | 关键子问题、必备事实、常见陷阱都有对应条目 | 漏掉会让好报告丢分的点了吗？ |
| 可判定 | 原子（一条只判一件事）、二元（是/否）、自包含（judge 只看报告与条目即可判） | 两人判会一致吗？还能再拆吗？ |
| 加权合理 | 核心事实权重压过琐碎与格式 | 最省力的满分路径，走的是真正重要的东西吗？ |
| 抗刷分 | 引用查"支撑性"而非"存在性"，配负分陷阱条目，不按长度和引用数给分 | 不做真研究能骗到分吗？ |
| 答案正确 | 条目隐含的事实本身正确且未过期 | 这条的"正确答案"是最新的吗？ |

> 来源：原子化与二元化取自 FActScore、TICK；语义加权与 self-contained 取自 RaR；抗刷分对应 OnlineRubrics 对 reward hacking 的讨论。

### 3.3 题、标、源三者对齐

- **双向覆盖**：instruction 要求的每点 rubric 都查；rubric 不增加 instruction 未提出的隐含条件。
- **难度匹配**：条目不能严到必然全错，也不能松到必然全对。
- **gold 可支撑**：参考来源能推出参考答案，且是存活的一手来源。
- **口径一致**：语言、时间、地域在三者间统一。
- **有区分力**：评一强一弱两篇报告，分数要拉开。

难度这一条值得单独强调：GRPO 下同一道题所有 rollout 全对或全错时，奖励方差为 0，梯度为 0，这条数据对训练零贡献。所以"一搜即得"和"根本无法证实"两端都要废弃。

### 3.4 常见设计错误

- **instruction 侧**：模糊欠规定、一搜即得、不可验证、无边界、诱导带偏、题干含答案、时间敏感却无日期锚、不安全违规、模板化、依赖不可访问的私有数据、交付物自相矛盾。
- **rubric 侧**：标准含糊、复合捆绑、不可核验、权重失衡、可被刷分、向 judge 泄露答案、条目间自相矛盾、要求报告里根本看不出的东西。
- **Deep Research 特有**：被引来源不支持 gold、答案随时间失效、gold 链接失效、仅凭语气笃定和有引用就给分、gold 本身存在争议、题目基于不实前提。

## 四、单条质检流程与工具

单条控制在 10–20 分钟。能批量扫的交给工具，人只复核工具标出的可疑项。

| 步 | 动作 | 工具 |
|---|---|---|
| 1 | 读 `instruction` 与 `metadata`，按 3.1 评题，任一条不达标直接拒 | LLM-as-judge 预筛模糊、主观、诱导项 |
| 2 | 核 gold：逐个打开 `reference_sources`，确认链接存活、是一手来源、能支撑参考答案，且答案当前仍成立 | DeepResearch-Bench FACT、RAGAS / TruLens、FActScore 式事实核验 |
| 3 | 按 3.2 评 rubric，并与 instruction 双向对齐（3.3） | LLM-as-judge 找复合、重复、矛盾、可刷分条目 |
| 4 | 扫完整性：近重复、抄公开 benchmark、死链、PII/版权、标签与编码（批量做法见第五节） | MinHash / 语义去重 / n-gram overlap |
| 5 | 试评：评一强一弱两篇报告，分数拉不开即不合格；再评一篇凑字数堆引用的低质报告，仍得高分也不合格 | DeepEval / promptfoo |
| 6 | 下结论：accept / edit / reject，定位到字段并写明改法 | Label Studio、Argilla |

批量生产还需三项管控：掺入已知答案的金标题，检测标注是否认真；多人判同一条算 IAA（Cohen's κ / Krippendorff's α），偏低说明 rubric 过于主观；初判 → 复核 → 仲裁三级审核，并用校准集统一标准。

第 5 步是最容易被跳过、但最能暴露问题的一步：一份 rubric 哪怕每条都写得漂亮，如果拿它去评一好一坏两篇报告分数拉不开，它对 RL 就是无效数据。

## 五、批量数据清洗

单条质检看"这条对不对"，清洗看"整批能不能用"。顺序：先去重，再筛质量，最后配多样性。

**去重**

| 层次 | 方法 |
|---|---|
| 完全重复 | 归一化（大小写、空白、全半角）后哈希 |
| 字面近重复 | MinHash + LSH，Jaccard 阈值约 0.8 |
| 语义重复 | embedding 聚类，簇内留一条；阈值过严会误删合理变体 |
| 评测集污染 | 与公开 benchmark 做 n-gram overlap，命中即剔除 |

同簇保留 rubric 更完整、来源更权威的那条。

**质量**：三道筛子由便宜到贵——规则筛（字段缺失、乱码、链接不可达、PII）→ LLM-as-judge 按 3.1 / 3.2 打分 → 人工只看标红。小规模高质量优于大规模噪声（LIMA / Deita），RL 阶段错误的 rubric 会直接把模型带偏；难度要分层，保留一部分模型当前解不出的题，否则贡献不了梯度。

**多样性**：按领域、任务类型（事实查证、对比、时间线、因果、汇总）、推理跳数、语言与地域、来源类型、时效性统计分布，占比过低的定向补数、过高的下采样；同模板合成题要设配额。

一个工程注意点：批量探测 `reference_sources` 存活时，只允许公网 `http/https`，并禁止解析到内网地址（`127.`、`10.`、`172.16-31.`、`192.168.`、`169.254.` 等），否则这个探活脚本本身就是一个 SSRF 入口。

## 六、数据飞轮：线上失败任务自动回流

目标：线上暴露的失败任务自动转成训练数据，人只在发版前确认一次。

### 6.1 Badcase 扩充

只修暴露出的那批 case，模型容易记住个例而不泛化，需要先扩样本。

**向量召回**

| 步骤 | 做法 |
|---|---|
| ① 编码 | 用冻结的编码器把失败任务的 `instruction` 转成向量 |
| ② 聚类 | KMeans 聚类，得到错误类型簇，如多跳检索中断、引用与声明不符、时间口径错误 |
| ③ 检索 | 以簇中心为 Query 在候选问题池做 ANN 检索，召回同类任务 |

相似度阈值要控制：过高召回的是重复题，过低则不是同类。

**数据合成**：用更强的 Teacher Model 对失败任务做变异。一是换问法，研究对象不变，改成反向提问或加入陷阱条件（如把时间锚换成另一个季度）；二是改约束生成对照题（换地域、换统计口径），并同步产出对应的 rubric 条目与参考来源。

### 6.2 回归评测

防止修好一类任务、搞崩另一类。测试集分两部分：

- **基础盘**：固定不变，覆盖 BrowseComp / GAIA / DeepResearch-Bench 等公开 benchmark 的变体；
- **错题本**：每周从线上失败任务更新。

发版门槛：基础盘能力波动不超过绝对值 1%。

人工全量评测成本过高，用 LLM-as-a-Judge 做新老模型对比：把 V_old 报告、V_new 报告、参考答案和 rubric 一起给 Judge，判断是否退化。

```text
给定研究任务与 rubric，老模型报告 A，新模型报告 B，参考答案 C。
按 rubric 逐条打分，判断新模型相比老模型是否退化。
若退化，输出 [REGRESSION] 并指出丢失了哪些事实、引用或覆盖点。
```

### 6.3 闭环流程

```
线上埋点 → 低置信过滤 → Teacher 重做 → 持续训练 → 发版门禁 → 回到线上
```

| # | 环节 | 做什么 | 产物 |
|---|---|---|---|
| 1 | 埋点 | 记录 `[instruction, 检索轨迹, 报告, 置信度]`，收集隐式反馈（改写问题重问、提前中止）与显式反馈（踩/赞） | 原始 Session |
| 2 | 过滤 | 每日离线筛出 Logprobs 过低、引用核验未通过或有负反馈的 Session | 新增 Badcase |
| 3 | 纠偏 | 交给 Teacher Model 重做研究，并对照报告补齐 rubric | `[instruction → 检索与推理过程 → 带引用报告]` 训练对 |
| 4 | 训练 | 合入训练池，每周触发一次（SFT 全参或 LoRA，或以 rubric 为 reward 做 RL） | 新 Checkpoint |
| 5 | 门禁 | 自动跑基础盘与 Judge 回归，Win Rate 高于基线且无退化才放行 | 迭代报告 |

人工只需看报告（修复了哪些错误簇、基础能力波动多少），确认后发布。

## 七、和通用 SFT / RL 数据工程的异同

清洗那一层基本是通用的，差异集中在"质量"怎么定义。

**通用部分**：去重（精确 / MinHash / 语义）、评测集污染检测、规则清洗（乱码、截断、字段缺失、PII、版权）、多样性配比，以及"规则筛 → 模型筛 → 人工只看标红"的三级漏斗。这些与训练范式无关。

**"质量"的定义随范式变化**

| 范式 | 一条数据是什么 | 质量 = |
|---|---|---|
| SFT | prompt + 目标回答 | 回答本身正确、风格一致；常用拒绝采样 / best-of-N 从强模型筛示范 |
| RLHF / DPO | prompt + chosen / rejected | 偏好标注的一致性，以及对子的区分度（差距太小则标注噪声大） |
| RLVR | prompt + 可验证答案 | label 正确且唯一，校验脚本无假阴性 |
| RaR | instruction + rubric | rubric 本身的覆盖、可判定、抗刷分 |

所以本文第三、四节在 SFT 数据工程里是不存在的，对应位置换成"示范回答的审核"——质量重心从"答案"挪到了"评分标准"。

**RL 独有的两个约束**：一是难度与奖励方差，全对或全错的题梯度为 0，需要按通过率分桶做课程式采样，这在 SFT 里没有对应物；二是 prompt 分布必须贴近线上，RL 是在 prompt 分布上优化策略，分布偏了就是优化错方向——这也是第六节数据飞轮要从线上埋点取题的原因。

此外还有两点程度差异：RL 对污染更敏感（污染题直接变成可被刷的高 reward），对标注一致性要求更高（IAA 低意味着 reward 本身是噪声，而 SFT 的标注分歧只是风格不统一）。

一句话总结：**清洗流水线可以照搬，质量判据要按范式重写。**
